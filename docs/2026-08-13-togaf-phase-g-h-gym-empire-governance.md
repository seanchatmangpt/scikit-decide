# TOGAF Phase G/H — Gym Empire Implementation & Change Governance

Scope: the ~13-repo "gym empire" under `seanchatmangpt/*gym*` plus `ggen`,
`ggen-marketplace`, `gymact` — as inventoried this session via `gh api`
(descriptions, topics, issue counts, tree listings). This document is
governance design only; no repo state, issue, or PR was modified while
writing it.

## Hard constraint (binding on every section below)

> No autonomous merge, close, delete, or register action may execute
> against any repo in this portfolio without an explicit user-in-chat
> approval for that specific action. No standing pre-authorization,
> label, schedule, or "trusted bot" role substitutes for that approval.

Every mechanism proposed in Phase G and Phase H is designed around this
constraint, not despite it. Where an automation is described, its output
is a **report or a flagged draft**, never a completed mutation.

## Standing vocabulary carried in from `.claude/rules/standing-law.md`

Governance findings below reuse the same statuses so they compose with the
rest of this repo's evidence discipline: `ALIVE`, `PARTIAL_ALIVE`,
`BLOCKED:<reason>`, `BUILD_BROKEN`, `UNKNOWN`, `UNSUPPORTED`. A repo whose
README describes a pipeline the tree does not contain is `UNKNOWN` for that
capability, never `ALIVE` — README prose is not evidence of code.

## Phase G — Implementation Governance

Phase G in TOGAF governs the transition from approved architecture to
in-production reality: conformance review of implementation projects
against the target architecture, and controlled deployment.

### G.1 Governance board and its actual authority

- **Board of one**: the user, in chat, per action. This document does not
  create a committee, a bot with merge rights, or a delegated approver.
  Any future proposal to add a second human approver is a change to this
  constraint and must be approved the same way — explicitly, in chat.
- **No service account holds write scope beyond what a specific,
  already-approved action needs.** A CI token that can open a PR is not
  the same grant as a token that can merge one; the latter is never
  provisioned for unattended use under this governance model.

### G.2 Conformance review — what gets checked, and by whom

For each repo in the portfolio, Phase G conformance review answers three
questions, using this session's discovery method (`gh api` metadata +
non-recursive tree + README fetch, never assumed):

1. **Does the tree contain what the README claims?** (bootstrap-only vs.
   substantive — `gymact` substantive; `fdegym`, `awesome-ai-gyms`,
   `ww3gym`, `rrgym`, `lifegym`, `biblegym`, `claudecodegym`, `chatgptgym`
   were bootstrap/README-only or feature-branch-only at last check.)
2. **Does the default branch match the branch the README describes as
   authoritative?** (`chatgptgym`'s default branch was
   `agent/chatgpt-cloud-gym`, not `main` — a conformance flag by itself,
   not a defect: it means "authoritative" and "default" have diverged and
   a human should decide which one governs.)
3. **Does any cross-repo bridge claim (e.g. "gymact.providers entry
   point", "ggen sync run", pinned commit SHAs in `ggen/*-pack`) resolve
   to a real, checked-out artifact, or is it aspirational prose?**

This review is **read-only** end to end. It produces a conformance report
per repo, not a merge, not an issue close, not a branch delete.

### G.3 Controlled deployment gates

Every repo-to-repo dependency this portfolio declares (e.g. `ggen-marketplace`
pinning a commit SHA from `ggen`, `*gym` repos pinning a `gymact` commit)
is a deployment gate. Phase G governance requires, before any such pin is
advanced:

1. A human-readable diff of what changed between the old and new pinned
   commit, generated by automation.
2. Explicit user approval in chat to advance the pin — this is a mutation
   (a commit), so it is squarely inside the hard constraint, not an
   exception to it.
3. No "auto-bump on green CI" pattern. Green CI on the *dependency* repo
   says nothing about the *consuming* repo's fitness for that version —
   conflating the two was exactly the class of error
   `no-dual-bookkeeping.md` already names for this codebase's own
   evidence graph, and it applies identically to a dependency graph.

### G.4 What "done" looks like for a Phase G review cycle

A Phase G cycle for one repo is complete when a report exists stating,
per repo, per capability claimed in its README:
`ALIVE | PARTIAL_ALIVE | BLOCKED:<reason> | UNKNOWN`, plus the exact
command used to establish that status (mirroring this repo's own
`standing-law.md` evidentiary bar). The cycle does **not** include taking
any action on the findings — that is Phase H.

## Phase H — Architecture Change Management

Phase H governs how change requests are detected, triaged, and acted on
once the architecture is live — the ongoing loop, not the one-time
transition.

### H.1 The two lanes, split by mutation risk

This is the load-bearing design decision for the whole document: **split
every recurring governance task into a read-only lane and a
human-gated-write lane, and never let a task cross from the first into
the second without a chat approval that names the specific action.**

#### Lane A — safe to run unattended (read-only / reporting only)

These may run on a schedule (e.g. via `RemoteTrigger`/cron) with zero
per-run approval, because their only output is information:

| Automation | What it does | Output |
|---|---|---|
| Drift detection | Re-run this session's `gh api` discovery pattern (metadata + tree + README) per repo; diff against last recorded snapshot | A dated report: what changed (new files, branch default changed, description changed, issue count delta) |
| Staleness flags | Compare `pushed_at` against a threshold (e.g. 30/90 days) per repo | A flagged list, no side effect |
| Bootstrap-to-substantive transition detection | Flag when a repo's non-recursive tree grows past `README.md`-only | A flag for human review — "this repo may now warrant a real conformance pass" |
| Pin-staleness detection | Compare a consuming repo's pinned commit SHA against the dependency repo's current HEAD | A diff report, not a bump |
| Default-branch/README mismatch detection | Flag when README says "canonical work is on X" but `default_branch` is `main` (or vice versa) | A flag, e.g. the `chatgptgym` case above |
| Orphan/duplicate detection | Flag near-duplicate repo purposes (e.g. overlapping "bounded GymAct-compatible world for X" READMEs) for human consolidation review | A candidates-for-review list |
| Open-issue triage summary | Summarize open issue titles/counts per repo (read-only `gh api`/`gh issue list`) | A digest, no issue is closed or labeled |

None of Lane A ever calls a mutating GitHub API (`merge`, `close`,
`delete`, label-apply that changes triage state, branch delete, repo
create/register into a catalog). If an automation's output is "and then I
did X to the repo," it is not Lane A by definition — it belongs in Lane B
below, however small X is.

#### Lane B — always requires a human click, per action, in chat

| Action | Why it can't be Lane A |
|---|---|
| Merging any PR | Irreversible-in-effect; changes what ships |
| Closing an issue | Discards triage state; a bot closing based on a heuristic (e.g. "stale") is exactly the standing pre-authorization pattern this document forbids |
| Deleting a branch, tag, or repo | Destructive; matches the CLAUDE.md-level "prohibited" list this project already treats as never-automatable |
| Registering a repo/pack into a marketplace or catalog (e.g. `ggen-marketplace` admission) | Changes what downstream consumers trust as canonical; admission is a governance decision, not a mechanical check |
| Bumping a pinned dependency commit SHA | A real behavior change for the consuming repo, per G.3 above |
| Renaming a repo, changing its default branch, or changing topics/description | Changes discoverability and the "authoritative" signal other automation and humans key off |
| Applying a label that gates further automation (e.g. "approved," "ready-to-merge") | Would silently promote a Lane A finding into a Lane B trigger without the human step this document requires |

### H.2 The review cadence

- **Weekly drift/staleness report** (Lane A, unattended): one digest
  covering all repos in the portfolio, delivered as a report artifact or
  chat summary — never auto-acted-on.
- **Human review session, cadence set by the user, not by automation**:
  the user reads the Lane A digest and decides, per flagged item, whether
  to direct a Lane B action. Each such direction is itself the "explicit
  user approval in chat" the hard constraint requires — a scheduled
  *review* is fine; a scheduled *action* is not.
- **No auto-escalation.** A staleness flag aging past N days does not
  itself authorize any Lane B action, no matter how long it has been
  flagged. Aging is data, not consent.

### H.3 Change request lifecycle

```text
Lane A automation detects a candidate change
        |
        v
   Reported to user (digest / chat message), status = "flagged"
        |
        v
   User reviews, decides per item: approve / defer / reject
        |
        v
   If approved: user explicitly directs the specific Lane B action
   (e.g. "merge PR #14 on gymact", "bump ggen pin in ggen-marketplace
   to commit c37b460")
        |
        v
   Lane B action executes with that action's own audit trail
   (commit, merge commit, or API call log) — never inferred after
   the fact, matching this repo's own no-dual-bookkeeping doctrine:
   the action log is the record, not a derived summary of it.
```

A flagged item that is never approved simply stays flagged. There is no
timeout that converts "flagged" into "approved."

### H.4 What must never be built, named explicitly

To keep this constraint from eroding by increment, the following are
named as **out of scope permanently**, not merely "not yet built":

- A bot account with a personal access token scoped to `merge`, `delete`,
  or repo-admin, run on any schedule.
- A GitHub Actions workflow that auto-merges on `label: approved` where
  the label itself was applied by another automation rather than a human.
- A "dry-run today, live tomorrow" staged rollout of any Lane B action —
  staging does not change the constraint; live execution still needs the
  approval, on the day it runs, not by inheritance from a dry-run's
  success.
- Batch approval ("approve all 12 flagged pin bumps") standing in for
  per-action approval — a single chat message naming all 12 actions
  individually satisfies the constraint; a single message approving a
  *category* of future action does not, because it is exactly the
  standing pre-authorization the constraint rules out.

## Cross-reference to this repo's own evidence law

This governance model is the TOGAF-Phase-G/H expression of doctrine
already load-bearing elsewhere in this repo:

- The Lane A/Lane B split is `absence-is-not-evidence.md`'s lattice
  applied to automation trust: "detected as stale" is not "authorized for
  deletion," the same way "not observed to be inapplicable" is not "known
  applicable."
- "The action log is the record" in H.3 is `no-dual-bookkeeping.md`
  applied to governance: a summary dashboard saying "12 repos reviewed
  this week" is a reporting projection, never the authority for what was
  actually approved — that authority lives only in the chat approval and
  the resulting commit/merge record.
- Per-repo conformance status using `ALIVE`/`PARTIAL_ALIVE`/`BLOCKED`/
  `UNKNOWN` in G.4 reuses `standing-law.md` directly rather than inventing
  a parallel vocabulary — this document does not introduce a second
  status system for the portfolio to drift against.
