# PRD/ARD — autofde-lab v26.8.11: Fortune-5 TOGAF Needs, Phase A Sourced from DSPy Signatures/Modules

## Executive summary

This document is the synthesis of the entire session's findings — the
autonomic loop doctrine, the OCPM/object-centric conformance gap, the
exhaustive (and negative) audit of `ggen`/`ggen-marketplace`'s external-
ontology-ingestion capability, the TOGAF ADM phase mapping, and the
Phase-A root-of-trust-corruption analysis — into one PRD/ARD targeting
`autofde-lab` v26.8.11. It answers the session's final open question
directly: **what happens when Phase A is sourced from DSPy Signatures and
Modules instead of human prose or ingested public ontologies.**

**Short answer, expanded below**: DSPy Signatures make Phase A **typed and
diffable** instead of free-text — a real, valuable reduction in the
corruption surface this session already identified (a typed
`InputField`/`OutputField` contract is trivially reviewable in a way a
prose "architecture vision" document is not). DSPy Modules and their
optimizers (GEPA, MIPROv2, BootstrapFewShot — all real, already used in
this repo via `gepa_train.py`) make Phase A **improvable against a real
metric** instead of static. But this does not remove the root-of-trust
problem two turns ago named — it **relocates** it to the metric/reward
signal the optimizer compiles against, and if that signal is
self-certified (an LLM judging its own Signature's output with no
independent verifier), it reproduces the exact laundering failure this
repo's `no-dual-bookkeeping.md` already forbids, wearing DSPy's syntax
instead of a human architect's. Nothing here changes
`fde-authority-boundary.md`'s ceiling: a DSPy-compiled Phase A artifact is
a `technical consequence`, never an `adoption decision`.

## What "Phase A from DSPy Signatures and Modules" concretely means

### 1. The Signature *is* the Statement of Architecture Work

Instead of a human-authored vision document or (per this session's audit)
a nonexistent external-ontology ingestion, Phase A's output becomes a real
DSPy `Signature`:

```python
class InferArchitectureVision(dspy.Signature):
    """Given observed enterprise state and a business objective, produce a
    typed architecture vision -- never free prose."""
    observed_state: str = dspy.InputField(desc="admitted OCEL-derived facts")
    business_objective: str = dspy.InputField()
    stakeholder_concerns: list[str] = dspy.InputField()
    vision: ArchitectureVisionModel = dspy.OutputField()  # a real pydantic model, per dspy-pack's hasPydanticModelType convention
```

This is a **real, structural improvement** over both prior candidates
this session considered: it's diffable/reviewable the way prose isn't
(closing part of the Phase-A-corruption gap two turns ago named), and it
doesn't depend on the ggen/ggen-marketplace external-ingestion pipeline
this session found doesn't exist.

### 2. A DSPy Module compiles the Signature; an Optimizer improves it against a real metric

`dspy.ChainOfThought(InferArchitectureVision)` or a `Pipeline`/`MultiHop`
composition (dspy-pack's real, verified module set) executes it.
`GEPA`/`MIPROv2` (also real, dspy-pack-verified) can tune the module
against a metric function — but **the metric is the new root of trust**,
and per this repo's own `no-dual-bookkeeping.md`, it may never be the same
LLM grading its own output. The metric must be a real, independently
computable function — e.g., "does the resulting `ArchitectureVisionModel`,
once run through `world_transformation_orchestrator.py`'s real
`compute_delta`, actually reduce the real delta against the real
`ScenarioMetadata`" — an external, checkable signal, not a self-report.

### 3. What this does NOT change

- **`fde-authority-boundary.md`'s seven-kind table is untouched.** A
  DSPy-compiled `ArchitectureVisionModel` is a `technical consequence`,
  produced by a Module, evaluated by a metric — it is explicitly not a
  `customer authority grant`, `adoption decision`, or `sunset
  authorization`. Those three still require the accountable named human
  the table already specifies. DSPy did not close that ceiling; nothing
  can, by this repo's own already-established, independently-derived law.
- **Root-of-trust corruption at Phase A is narrowed, not eliminated.**
  Corrupting a typed `Signature` + a real, external metric function is
  harder than corrupting a prose vision document (smaller diff surface,
  checkable metric), but a compromised human who controls *both* the
  Signature's authoring AND the metric function's implementation can still
  launder intent — the same threshold-authorization/meta-policy mitigation
  named two turns ago (k-of-n sign-off on Signature changes; a metric
  function that itself lives outside the Signature-author's edit surface)
  is still the real fix, not obviated by DSPy.
- **The ggen/ggen-marketplace external-ingestion gap is still real and
  unbuilt.** DSPy Signatures are proposed here as v26.8.11's Phase-A
  mechanism precisely *because* that pipeline doesn't exist — not as a
  reason to stop caring that it doesn't.
